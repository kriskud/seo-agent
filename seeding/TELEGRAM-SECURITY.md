# Обязательные требования к будущему Telegram listener

Telegram — будущая фаза. Этот документ фиксирует ограничения архитектуры;
listener и подключение существующей сессии сейчас не реализуются.

## Модель угроз

Другие пользователи сервера могут иметь обычный SSH-доступ под своими Linux
users. Они не должны получать Telegram credentials, личную сессию или данные,
позволяющие авторизоваться от имени владельца аккаунта, через repository,
git history, application directory, logs, process arguments, общее окружение,
общие конфиги или group/world-readable файлы.

От root или пользователя с unrestricted sudo защитить сессию средствами того
же сервера невозможно. Нельзя обещать такую защиту. Если этот риск неприемлем,
нужна другая граница доверия, например отдельный сервер.

## Хранение и изоляция

- Запуск только под отдельным Linux-пользователем, например `seoagent`, не под
  общим пользователем проекта. Другим людям нельзя предоставлять доступ к этому
  UID или возможность запускать произвольный код от его имени.
- Secrets вне repository и application directory, например
  `/etc/seo-agent/secrets/`; сессии — `/var/lib/seo-agent/telegram/`.
- Secret/session directories: строго `0700`; secret/session files: строго `0600`.
  Owner — UID пользователя listener. Никаких дополнительных ACL, предоставляющих
  доступ другим пользователям. Родительские каталоги не должны позволять другим
  пользователям подменять пути или файлы.
- В эти же ограничения входят SQLite journal/WAL/SHM, временные файлы и резервные
  копии сессии. Процесс должен создавать их с ограничительными правами (`umask 077`).
- Запрещено хранить в git **или директории приложения**, включая игнорируемые
  файлы: session/StringSession, Telethon/GramJS `.session`, `api_id`, `api_hash`,
  телефон, коды входа, 2FA password, bot tokens, cookies и любые auth artifacts.
- Telegram secrets нельзя добавлять в существующий общий `.env` приложения.
  Нельзя передавать их в CLI arguments или общих environment/config files.
  Предпочтителен ввод через защищённые файлы; конкретный механизм предстоит
  согласовать при проектировании listener.
- Никаких credentials/session strings в stdout, logs, errors, debug output,
  дампах конфигурации или диагностике сторонних Telegram-библиотек.
- Runtime-код, зависимости и unit-файлы, исполняемые под `seoagent`, не должны
  быть доступны другим SSH-пользователям для записи: иначе они смогут внедрить
  код, читающий сессию с правами listener. Это относится и к общему checkout.

`.gitignore` — только дополнительная защита от случайного добавления файлов.
Он не запрещает создание файлов, не распознаёт секреты внутри произвольно
названного файла, не защищает tracked files и не очищает git history.
Запрет хранения действует независимо от имени файла и ignore patterns.

## Данные и доступ к Telegram

- Listener read-only по назначению: без отправки сообщений, реакций, вступления
  в сообщества или других действий, изменяющих аккаунт/чаты. Это ограничение
  приложения, а не утверждение, что личная Telegram-сессия имеет read-only права.
- Только явный allowlist конкретных групп/каналов для CosmoDesk. Пустой или
  отсутствующий allowlist означает отсутствие доступа, а не «читать всё».
- Личные диалоги и Saved Messages исключены. Нельзя читать историю, подписываться
  на обработку содержимого или сохранять сообщения источников вне allowlist.
  При реализации нужно проверить поведение выбранной библиотеки для входящих
  updates; нельзя считать глобальную подписку безопасной только из-за поздней
  фильтрации перед записью в БД.
- Не создавать архив переписки. Хранить только минимальные данные релевантной
  opportunity: chat/channel identifier, message identifier, public/deep link
  при наличии, текст сообщения, timestamp и classification metadata, когда
  соответствующая фаза появится. Не сохранять контакты, полный профиль аккаунта,
  нерелевантные сообщения или необязательные вложения.
- Session/authentication information никогда не попадает в opportunities.
  Даже минимальные opportunity-данные из закрытых групп могут быть приватными:
  доступ к их хранилищу и логам нужно определить отдельно до подключения сессии.

## Fail closed

До чтения secrets, инициализации Telegram-клиента или сетевого подключения
listener обязан проверить владельца, тип файлов, права директорий/файлов и ACL.
Символические ссылки и подмена путей не должны обходить проверку; открытие и
проверка должны быть спроектированы с учётом race conditions.

При неверном владельце, слишком широких правах, небезопасном пути, недоступной
проверке или некорректном allowlist — отказ запуска с ненулевым exit code и
безопасной ошибкой без содержимого secrets. Например, session с `0644` запрещена.
Не исправлять права молча и не продолжать работу с предупреждением.

## Обязательная проверка перед реализацией подключения

Сначала представить пользователю конкретное предложение:

1. Linux user/UID, доступ к нему и права на исполняемый код.
2. Пути secrets/session, ownership, modes, ACL и права родительских каталогов.
3. Полный proposed systemd unit: `User`, `Group`, `UMask=0077`, способ передачи
   secret paths, доступные для записи каталоги, ограничения файловой системы,
   логирования/debug/core dumps; совместимость с используемым systemd.
4. Явный allowlist источников и правила минимизации/доступа к opportunity-данным.
5. Проверки отказа для `0644`, неверного владельца, небезопасных каталогов,
   symlinks/ACL, отсутствующего allowlist и утечки secrets в ошибки/логи.

Только после проверки пользователем этой конфигурации подключать его существующую
Telegram-сессию. Наличие сессии или разрешение на Phase 1 не является разрешением
на её импорт, копирование, чтение или подключение.
